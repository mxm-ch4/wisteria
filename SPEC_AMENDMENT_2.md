## 1. Версии

| Уровень | Версии | Что гарантируем |
|---|---|---|
| **Tier 1 (основной)** | **26.2** | Полный функционал, живые тесты, Grim-матрица |
| **Tier 2** | 26.3, 26.1.x | Билд собирается, клиент стартует, smoke-тест (GUI/HUD/ключевые модули). Полный регресс — по запросу |
| **Tier 3** | будущие 26.x | Порт по мере выхода, по тому же шаблону |

Автотест `runClientGameTest` из этапа 0 — это **шлюз версии**: версия считается поддержанной только если он зелёный на ней.

### Архитектура под мульти-версию (закладывается с первого дня, дёшево сейчас, дорого потом)
Разведка этапа 0 показала, что 26.2 → 26.3 это не пересборка: рендер-слой переехал (`com.mojang.renderpearl`), ввод перешёл с GLFW на SDL, изменились пакеты и звук. Значит:

1. **Слой совместимости `compat/`.** Модули, GUI, HUD и ядро **не вызывают** рендер, ввод, звук и сетевые классы игры напрямую. Только через собственные интерфейсы: `Renderer2D`, `Renderer3D`, `InputBackend`, `AudioBackend`, `PacketAdapter`.
2. **Реализации по версиям:** `compat/v26_1`, `compat/v26_2`, `compat/v26_3`. Общий код (логика модулей, дизайн-система, конфиги) один на все версии.
3. **Сборка.** Выбрать в этапе 0 живым тестом: Stonecutter (препроцессор/мульти-версия) или аналог. Критерий: один репо, один исходник логики, N jar на выходе.
4. **Правило ревью:** любой прямой импорт `net.minecraft.client.render.*`, `GLFW`/`SDL`, звуковых классов вне `compat/` = ошибка сборки (проверка в Gradle или checkstyle).
5. `docs/version-matrix.md`: таблица «версия → автотест → что в compat отличается → известные баги».

Честная цена: на каждый новый дроп уходит порядка 1–3 дней на compat-слой. Это закладывается в план, а не удивляет потом.

## 2. Что значит «лучше Wurst»

Wurst — хорошая стабильная база, но у него простые инструменты. Наши отличия — не «больше модулей», а **качество и интеллект** ключевых:

| Фича | Что у Wurst (по общему знанию, сверить на этапе 0) | Что делаем мы |
|---|---|---|
| X-Ray | фильтр отображения по списку блоков | см. раздел 3 |
| BaseFinder | поиск по типам блоков, построенных игроками | см. раздел 4 |
| Fly | набор простых режимов | см. раздел 5 |
| GUI/HUD | функциональные | дизайн-система, анимации, темы (этапы 2–4) |
| Данные | без постоянной памяти | **персистентная БД чанков/находок**, карта-оверлей |
| Античит | без учёта | **Grim Lab**: авто-журнал флагов (раздел 6) |

## 3. Xray «качественный»

Цель: не «вкл/выкл», а инструмент, которым реально ищут и добывают.

1. **Режимы отображения:** (а) фильтр рендера по списку блоков, (б) ESP-контуры руд сквозь стены, (в) гибрид. Переключаются на лету.
2. **Не мыло, а читаемость:** контуры с глубинным затуханием (fade по расстоянию), цвета по типу руды, подписи (тип + размер жилы), настраиваемая прозрачность окружения, без просадки FPS.
3. **Кластеры жил:** руды группируются в жилы, показываем размер, центр, расстояние. Фильтр «жилы от N блоков».
4. **Y-слои и режимы:** подсветка оптимальных высот по руде, отдельный режим для Nether (ancient debris), пещеры/лава/спавнеры/подземные структуры.
5. **Интеграция с Baritone (PvE-ядро):** «идти и выкопать эту жилу» в один клик/бинд.
6. **Анти-xray серверы (Paper anti-xray):** если сервер маскирует руды, Xray должен честно показывать только то, что клиенту реально пришло, без ложных находок. Режим-детектор: «сервер скрывает руды» (по аномальной статистике блоков), пишет в HUD.
7. **Стретч (после v1):** предсказание по сиду мира. Реализация генерации руд/структур, оффлайн-карта. Оговорка: на старых мирах (как 2b2t) чанки генерировались разными версиями, поэтому предсказания там ненадёжны. Делать только если останется ресурс.

## 4. BaseFinder «Intel»

Цель: не список блоков, а **оценка вероятности «здесь что-то построено»** по нескольким сигналам. Полностью пассивный (Grim не затрагивается).

Сигналы (каждый даёт вес в общий скор чанка):
1. **Возраст чанка:** NewChunks/OldChunks (эвристики по потокам жидкости и порядку подгрузки), следы перемещения игроков.
2. **Неприродные блоки:** бетон, стекло, шерсть, терракота, обсидиан в необычных местах, факелы/фонари под землёй.
3. **Блок-энтити:** сундуки, шалкеры, бочки, воронки, раздатчики. Вычитать природные структуры (подземелья, шахты, форты, бастионы).
4. **Освещённость:** уровень света там, где природно невозможен.
5. **Рельеф:** выкопанные полости, ровные площадки, тоннели 1x2/2x2/3x3 (хайвеи, диагонали), аномалии карты высот.
6. **Сущности:** загоны с животными, фреймы, стойки, деревни-фермы.
7. **Фильтр природы:** вычитание известных структур по паттернам блоков (и по сиду, если он известен).

Выход:
- **Персистентная БД** (SQLite в `.minecraft/<client>/intel/`): координаты чанка, скор, сигналы, время, пометка пользователя.
- **Оверлей-карта и heatmap** в HUD/GUI в стиле дизайн-системы.
- **Экспорт вейпоинтов** (формат, совместимый с картами, проверить на этапе 0).
- **Ручная разметка:** пользователь помечает «ложное/настоящее», веса калибруются.
- **Интеграция с поиском маршрута:** «лететь/идти к наиболее вероятному чанку» (через travel-модули волны C).

## 5. Fly «Fly Lab»: честная постановка

Grim строит предсказание движения каждый тик: настоящий «свободный полёт» вне элитры/транспорта он режет. Поэтому «Fly любыми твиками» это не один режим, а **набор режимов + научный подход**:

| Класс | Идея | Устойчивость к патчам |
|---|---|---|
| A. Легитимная механика | Элитра: bounce, буст фейерверком, набор высоты, экономия прочности; транспорт; вертикаль через постановку блоков | Высокая: это нормальная симуляция |
| B. В пределах допусков | Микро-приращения в рамках допуска предсказания: низкие прыжки, глайд, сглаженные траектории | Средняя: зависит от версии и конфига Grim |
| C. Дыры конкретной версии/конфига | Расхождения между симуляцией клиента и предсказанием Grim | **Низкая:** живут недели, потом патчатся (в README чужого аддона часть режимов уже помечена «patched on 2b2t») |
| D. Визуальный Fly | Только на клиенте (Freecam), сервер не видит | Не флагается, но это не полёт |

Метод (Fly Lab):
1. **Читать исходники Grim** (открытый код) для версии на стенде: где допуски предсказания, какие проверки (Simulation/Prediction и т.д.), как обрабатывается ViaVersion.
2. **Реализовать «лимитер»:** модуль сам себя ограничивает, не выходя за измеренный порог (самотроттлинг скорости/ускорения).
3. **Режимы как пресеты с параметрами**, каждый со своей строкой в `docs/grim-matrix.md`.
4. **Дефолт строго класс A/B.** Класс C только отдельным тумблером «экспериментально» с пометкой в GUI.
5. **Помнить:** зелёный результат на стенде владельца ≠ зелёный на 2b2t (другая версия сервера, ViaVersion, конфиг). Итоговая проверка только на реальном сервере.

## 6. Grim Lab (dev-инструмент клиента)

Отличие, которого нет у других клиентов, и оно напрямую ускоряет твой живой тест:
- Клиент в режиме разработчика **парсит чат-алерты Grim** (владелец op, включены алерты), считает по модулю: проверка, VL, время.
- **Авто-заполнение** `docs/grim-matrix.md`/CSV: модуль, пресет, версия, сработавшие проверки.
- **Сценарии-прогоны:** кнопка «прогнать модуль на 5 минут и записать результат».
- Включается только флагом `--dev`/в конфиге, в обычном режиме не работает и не влияет на геймплей.
- Формат строки алертов зависит от версии/настройки Grim: сначала зафиксировать реальный вид алертов со стенда в `docs/grim-alert-format.md`, не угадывать регулярки.
