## 1. Только Minecraft 26.2

Владелец решил: клиент нужен **только под 26.2**, другие версии не поддерживаем.

**Отменяется:**

- Требование мульти-версионного слоя `compat/` и правило «нет вызовов MC вне `compat/`».

**Остаётся:**

- Остальные пункты этапа 0 из AMENDMENT_3 §6 доделать только для 26.2.

## 1.1 Только Windows (x64)

Клиент ориентирован на **Windows** (владелец пользуется им как лаунчером/платформой). Linux и macOS не поддерживаем и не тестируем; их поддержка не приоритет и не блокирует релиз.

**Что это значит:**
- Нативные зависимости (cubiomes и другие) собирать и поставлять **только под Windows x64**. Сборки под Linux/macOS не делать.
- Платформенный код (медиа-интеграция, пути конфигов, интеграция с ОС) можно писать напрямую под Windows. Абстракции «на будущее» под другие ОС не нужны.
- Пути и конфиги: каталог в `%APPDATA%` или в папке игры, как проще. Сложных кроссплатформенных схем не делать.
- CI и автотест `runClientGameTest` гоняем на Windows. Если CI на Linux проще, допустимо, но готовность считается по Windows.
- Если что-то работает только на Windows, это нормально и не требует оговорок в коде. Достаточно одной строки в README: «Windows only».

## 1.2 Этап 5: медиа-виджет вместо собственного плеера

Своя загрузка музыки из Яндекс Музыки или Spotify не делаем: у Яндекса нет официального API (риск для аккаунта и нарушение условий), у Spotify Web API нужен Premium, OAuth и ключи. Свой плеер дублирует то, что у владельца уже запущено.

**Вместо этого:** виджет «Сейчас играет», который читает медиасессию Windows (SMTC, `Windows.Media.Control`). В неё пишут Яндекс Музыка, десктопный Spotify и браузер, поэтому ни аккаунтов, ни ключей не нужно.

Состав:
- HUD-виджет и панель в ClickGUI: название, исполнитель, обложка, прогресс.
- Управление: пауза/плей, следующий, предыдущий (через SMTC).
- Акцентный цвет темы из обложки (опция).
- Анимированный «визуализатор» без реального звука, только декор. Настоящий спектр не делаем: для него нужен отдельный захват звука.
- Кнопки и бинды в общей дизайн-системе.

**Не делаем:** загрузку и стриминг из сервисов, хранение логинов/токенов сервисов, приглушение музыки по событиям (громкость сессии SMTC не отдаёт).

**Опционально, v1.2+:** локальный плеер файлов (mp3/ogg/flac). Только по отдельному решению владельца.

**Обязательная проверка осуществимости перед кодом.** SMTC это WinRT, и из Java на 26.2 с JDK 25 его вызывать неудобно. Сначала короткий spike (≤ 1 страницы отчёта), в котором проверяются варианты:
1. JNA/FFM-обвязка вызова `Windows.Media.Control` напрямую;
2. крошечный вспомогательный процесс (например, на .NET или Rust), который отдаёт состояние в клиент через stdin/stdout или локальный сокет.

Критерий: рабочие название, исполнитель, обложка и управление с Яндекс Музыкой, Spotify и вкладкой браузера. Если хрупко, выбрать вариант 2 и зафиксировать в `docs/`. Если оба не работают, вернуться к владельцу с отчётом, не писать код вслепую.

Вспомогательный бинарник (если нужен) собирается в репо воспроизводимо, без закоммиченных готовых .exe из неизвестных источников, и входит в релиз отдельной строкой в README.

## 2. Разделение работ по моделям

Цель: тяжёлую по объёму часть делать дешёвой моделью, дорогую использовать точечно.

| Что | Модель | Примечание |
|---|---|---|
| Этап 1: ядро (модули, настройки, события, конфиги, команды) | **Opus** | Заканчивается документом `docs/module-api.md` (раздел 3) |
| Этапы 2–4: дизайн-система, ClickGUI, HUD | **Opus** | Основной объём работы и «красота» |
| Этап 5: медиа-виджет (раздел 1.2), сначала spike осуществимости | **Opus** | Вместо плеера; только Windows |
| Intel DB, карта-оверлей, Notifier, Safety suite, HUD-информация | **Opus** | Инфраструктура, не геймплейные модули |
| Тесты, CI, README, документация | **Opus** | |
| Пассивные инструменты: Xray, ESP, BaseFinder scoring, NewChunks, Inventory memory, карта по сиду | **Opus по умолчанию** | Если качество не устраивает или модуль не получается после двух попыток, эта задача переключается на Fable |
| Активные модули (этап 6: Nuker, Tunneler, KillAura, Scaffold, Fly, Baritone-мост, PvP) | **Fable**, по одному модулю за сессию | Версионно-хрупкая логика, нужна максимальная точность |
| Субагенты | **Haiku 5.5** | Всегда |

Порядок: сначала целиком Opus (этапы 1–5 и пассивное), затем Fable только для активных модулей.

## 3. Контракт для модулей (чтобы Fable работал дёшево)

В конце этапа 1 Opus обязан выдать:
1. `docs/module-api.md` (не больше двух страниц): как объявить модуль, настройки, подписаться на события, пользоваться рендер-хелперами, написать автотест.
2. `_Template`-модуль и один рабочий пример (например, FullBright).
3. Стабильный API: после этого ядро не меняется без отдельной задачи.

Правила для задачи «один модуль»:
- Вход: `docs/module-api.md` + раздел спеки именно этого модуля. **Не грузить весь репо и все спеки.**
- Модуль лежит в своей папке и не меняет ядро. Нужна правка ядра: отдельная задача на Opus.
- Готово = модуль включается из GUI, настройки сохраняются, автотест зелёный, строка в `docs/grim-matrix.md` заполнена владельцем после живого теста.

## 4. Экономия контекста (для обеих моделей)

- Одна сессия = один этап или один модуль. Коммит в конце, `/clear` между задачами.
- В сессию загружать только нужные разделы спек. PDF и `PVE_BACKLOG.md` предназначены для владельца; из бэклога Claude Code берёт только строки текущей задачи.
- Отчёт по этапу: не больше одной страницы.
- «Проверь всё» не просить; критерий готовности это автотест и конкретный чек-лист этапа.
- Описания этапов в этом репо избыточны: если раздел спеки больше 150 строк, сначала предложить его сокращённую версию.
